Limitations

Each limitation below explains the issue, its effect on our results, and what we did about it (or what would fix it).

1. No loan dates

The issue
The dataset does not say when each loan was given. Interest rates depend strongly on the economy at the time: when the central bank raises its rate, every loan becomes more expensive.
Effect
We cannot study how risk or pricing changed over time, and we cannot match each loan to the economy at the moment it was issued, as the proposal originally planned. A random train/test split also cannot test whether a model trained on older loans works on newer ones.
What we did
We used the World Bank data as a plausibility check instead: we kept only the years in which the US prime rate was below the cheapest loans in the data, and used the average prime rate over those years (3.86%) as one fixed benchmark. With dates, each loan could be compared with the benchmark of its own year, and the split could be made by time.

2. How the grade is produced is not documented

The issue
The dataset gives each loan a grade A–G but does not say who assigned it or how. We treat it as a universal credit-history rating, available when someone applies, like a credit score such as CIBIL.
Effect
Pipeline A, our main pricing pipeline, depends on this assumption. If the grade is instead assigned by this lender only after its own assessment, Pipeline A can only be used after that step, and Pipeline B is the realistic setting for brand-new applicants. Pipeline A's high rate accuracy (R² 0.91) also reflects how closely this lender priced from its own grade; for another lender it may be lower.
What we did
We built and reported all three settings, so the results are available under either reading: Pipeline A if the grade is known at application, Pipeline B if it is not. The assumption is stated wherever Pipeline A is described.

3. Country not documented

The issue
The dataset does not say which country the loans come from. We assume the United States from its structure (dollar amounts, a $35,000 loan cap, and grades and home-ownership categories as used by US lenders).
Effect
The World Bank comparison uses US interest rates. If the loans came from another country, the benchmark (3.86%) and therefore all premiums would be different. The default and rate models themselves do not depend on the country.
What we did
The assumption is stated on the Data and Results tabs, and the World Bank part is presented only as a plausibility check, not as a result the models depend on.

4. Possibly partly simulated data

The issue
Real lending data is messy, but this data contains rules with no exceptions: every applicant who rents and borrows more than about 31% of income defaulted (about 1,870 people), and grades A and B contain no applicant with a past default. Default rates are also extreme: 22% overall and 98% in grade G (calculated from the data).
Effect
Clean, rule-like patterns are easy for tree models to learn, so our scores (for example F1 0.84) may be higher than the same models would reach on real loans. No real lender could keep lending at about 20% interest to a group where 98% default, so the defaults may not reflect real behaviour.
What we did
We report this openly (Result analysis, finding 7) and describe the results as results on this dataset, not on lending in general. Testing on a second, real dataset would show how much the scores drop.

5. Only approved loans (selection bias)

The issue
The data contains only loans that were actually granted. Applicants the lender rejected never appear, so we never see whether they would have repaid.
Effect
The models learn from an already-filtered group. When used on all applicants, including the kind the lender used to reject, their PDs may be too low, because such people are rare in the training data. This is a known problem in credit scoring (reject inference).
What we did
Nothing can fix this with this data. It would need records of rejected applicants, or methods that estimate how they would have behaved.

6. One dataset only

The issue
All models were trained and tested on one lender's data. The test set comes from the same data, only a different 20% of it.
Effect
The test result shows how the models do on new applicants of this lender. How they would do for other lenders, countries or time periods is untested.
What we did
We looked for a second dataset to check against (for example Lending Club), but key inputs such as age are missing there, so the same models could not be applied.

7. Information ceiling for newcomers

The issue
Without the grade, the only credit-history facts left are past default (yes/no) and length of credit history. The lender set rates mainly from the grade.
Effect
Pipeline B can predict a newcomer's rate only to about ±2.7 pp (R² 0.31), and its default decisions are weaker (F1 0.70 vs 0.84). Six different rate models all stopped at the same R² ≈ 0.30, so a better model would not help: the information is missing.
What we did
We tried predicting the grade first (two-stage model); it did not help (R² 0.303 vs 0.305). Pipeline B is therefore presented as a rough fallback, with Pipeline A as the main pricing pipeline.

8. The rate model copies past pricing, and the cutoff ignores money

The issue
The rate model is trained on the rates this lender actually charged. The approve/decline cutoff is chosen to maximise F1.
Effect
The suggested rate is what similar borrowers paid in the past, not a break-even or profit-maximising rate. F1 treats a missed defaulter (the lender loses most of the loan) and a wrongly declined good customer (the lender loses only the interest) as equally bad. A cutoff based on money would probably be stricter than ours (0.37–0.39): to break even on a borrower with a 37% chance of default, the rate would need to be roughly 35–60%, far above the 23% maximum in the data.
What we did
We state this as a limitation. With the loss per default and the lender's funding cost, the cutoff could instead be chosen to maximise expected profit, and a rate could be calculated from the PD.

9. Method details

The issue
Three shortcuts in how the models were built: (a) SMOTE was applied after one-hot encoding, so its synthetic applicants can have "in-between" categories (for example 0.4 renter); (b) the RBF SVM in Pipelines A and B was tuned on an 8,000-row subset, not the full training set; (c) the forest searches tried 15 random combinations, not every combination.
Effect
(a) The synthetic defaulters are slightly unrealistic. (b) and (c) The chosen settings may not be the very best possible.
What we did
(a) SMOTENC, which handles categories properly, would be the cleaner choice; SMOTE never improved F1 here and the final models do not use it, so this does not affect the final results. (b) The subset result was confirmed on the full training set in the Reference setting. (c) A full search might find slightly better settings, but the Random Forest was already the best model in every setting.

10. Correlation, not causation

The issue
The models learn which kinds of applicants defaulted in the past. They do not learn what causes default.
Effect
The PD cannot be used to answer "what if" questions. For example, a lower interest rate would not make a risky applicant safer in these models, even though in reality a lower repayment might reduce default. Likewise, telling an applicant to change one input would not necessarily change their real risk.
What we did
We use the models only for prediction (who is likely to default, what similar borrowers paid) and do not draw causal conclusions.

Reproduce

Everything on this site can be recreated from the repository: https://github.com/JohnShinoj/credit-risk. The README has the same steps.

1. Set up Python

Python 3.13 (tested with 3.13.11 on Windows; other systems should work). Create a virtual environment, install the exact package versions in requirements.txt, and register the environment as a Jupyter kernel:

python -m venv .venv
.venv\Scripts\activate            (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt
python -m ipykernel install --user --name ml-project-venv --display-name "ML project (.venv 3.13)"

Select the kernel "ML project (.venv 3.13)" in Jupyter or VS Code. Pinned versions matter: a different scikit-learn version can give slightly different numbers.

2. Get the data

  • Loan data: notebook 01 downloads the public Kaggle Credit Risk Dataset automatically with kagglehub. If it asks for credentials, create a free Kaggle account and an API token (Kaggle → Settings → API), or download credit_risk_dataset.csv by hand and point notebook 01 to it.
  • World Bank data: notebook 12 downloads it from the public World Bank API (no key needed) and saves a copy, so it only downloads once.
  • The data is not stored in the repository (it is recreated by the notebooks). The repository contains no private data, passwords or API keys.

3. Run the notebooks in order

Run each notebook from top to bottom. Later notebooks read files saved by earlier ones (the train/test split, the chosen settings in reports/), so the order matters. Times are for a 12-core laptop on mains power.

4. Rebuild the website data

Run python src/export_site_data.py. It reads the notebooks' saved results and writes the website's data files (docs/data/) and figures (docs/figures/). To view the site locally: python -m http.server 8765 --directory docs, then open http://localhost:8765.

Why the results come out the same every time

  • Fixed randomness: every random step (the split, the folds, SMOTE, the forests, the bootstrap) uses seed 42.
  • One split, saved: the train/test split is made once in notebook 01 and saved; every later notebook reads the same files.
  • Same folds everywhere: every model uses the same 5 cross-validation folds (src/credit.make_cv), so models are compared on exactly the same data.
  • No leakage: all learned preprocessing (filling gaps, scaling, encoding, SMOTE) sits inside the model pipeline, so it is learned from the training folds only.
  • Choices saved, test used once: every choice is made with cross-validation and saved in reports/; notebook 11 is the only notebook that opens the test set.
